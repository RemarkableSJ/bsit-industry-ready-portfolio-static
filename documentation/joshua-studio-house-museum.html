Joshua's Studio House Museum

A museum-inspired art gallery and storefront presentation for graphite portraits, canvas paintings, drawing supplies, studio products, and custom commission demonstrations.

Open Museum Demo ↗Back to Case StudyView Source README

1. Project overview

Joshua's Studio House Museum is a browser-based art gallery and storefront presentation. It organizes artwork, studio materials, drawing supplies, and selected products in a museum-inspired browsing experience. Visitors can move between exhibition areas, inspect items, filter collections, select variants where available, and try a demonstration cart and commission-request flow.

This portfolio version is intentionally a static presentation edition. It demonstrates the visitor interface and front-end interactions; it is not a live e-commerce service.

2. Problem and objectives

An art studio may need a more organized online presentation than separate social-media posts or manually shared photographs. A single gallery-style site can help visitors browse artwork, compare product options, and understand the commission-request process.

Organize collections

Present Graphite, Canvas, and Artisan Artifacts in clear exhibition areas.

Improve browsing

Demonstrate showroom navigation, image browsing, catalog filters, and product variants.

Show product choices

Display item details, sample prices, stock indicators, and defined variants.

Demonstrate user flows

Show a browser-local cart, simulated checkout, and commission request form without server transactions.

3. Main visitor journey

  1. Grand Hall: the visitor arrives at the museum-style landing section.
  2. Showrooms: the visitor browses Graphite Hall, Canvas Wing, and Artisan Artifacts.
  3. Exhibitions: the visitor opens the catalog and filters items by category.
  4. Product selection: the visitor inspects an item and chooses a variant where applicable. Displayed sample price and stock are updated from local demonstration data.
  5. Acquisitions cart: the visitor adds items, sees the cart count, changes quantities or removes items, and reviews the subtotal.
  6. Simulated checkout: the visitor can explore shipping or pickup options. No real order or payment is submitted.
  7. Patronage / commission request: the visitor can open the commission section and complete a demonstration form. It is not sent to a studio inbox.

4. Features

  • Museum/gallery landing page and navigation.
  • Graphite, Canvas, and Artisan Artifacts showroom areas.
  • Showroom image carousel controls.
  • Catalog and category filters.
  • Product cards with images and item details.
  • Variant selection for selected supplies and materials.
  • Dynamic sample price and stock display for defined variants.
  • Add-to-cart and remove-from-cart interactions.
  • Cart badge, quantities, and subtotal calculation.
  • Shipping/pickup demonstration choice.
  • Commission-type selection and request form presentation.
  • Responsive styling and 17 supplied artwork/product image assets.

5. Technology and architecture

HTML5

index.html provides the page shell, navigation, footer, and application root.

CSS3

styles.css contains the museum visual design and responsive styling.

JavaScript

script.js defines demonstration inventory, in-memory state, rendering, filtering, variant, and cart behavior.

Static assets

assets/images/ contains artwork and product photography used by the page.

External visual resources

The page loads Tailwind CSS, Lucide icons, and fonts from public CDNs. Internet access is needed for these external resources.

Browser state

The current cart and navigation state live in JavaScript while the page is open. Demonstration inventory is read from and written to browser localStorage under museum_demo_inventory. This is local to the current browser, not a shared or server-side database.

6. Data and transaction behavior

Presentation-only: this portfolio copy intentionally excludes real backend, payment, and remote-order behavior. It must not be represented as accepting real purchases, taking payments, reserving stock, arranging fulfilment, or sending commission requests to a staff inbox.

The initial inventory is defined in script.js. Variant stock changes can be saved in the current browser's local storage. The cart and simulated request interactions are not submitted to a business server.

7. Run locally

  1. Download or extract the portfolio repository.
  2. Open project-archives/joshua-studio-house-museum/.
  3. Start a local server from that folder:
python -m http.server 8000

Open http://localhost:8000/. Test showroom navigation, image carousels, filters, variant selection, cart interactions, simulated checkout, and the commission form. A local server is recommended for consistent browser handling of local assets and JavaScript modules.

9. Verification status

Static checks performed

  • JavaScript source syntax was checked.
  • Supplied local image references were checked against package assets.
  • The static presentation copy was checked to ensure real payment and external-order integrations were not included.
  • The expected page entry point, stylesheet, JavaScript, and image assets are included.

Manual checks recommended

  • Test navigation and showroom controls on desktop and mobile browsers.
  • Test each category filter and product variant.
  • Verify quantity limits and cart subtotals.
  • Confirm the simulated checkout clearly states that no real transaction occurs.
  • Confirm the commission demo does not imply that a real request was sent.
  • Re-test the deployed URL after significant changes.

10. Limitations and future work

  • No server-side application, database, visitor account, or administrator dashboard is included.
  • No real order, payment, webhook, inventory reservation, or fulfilment is performed.
  • Commission requests are local demonstrations and are not sent to the studio.
  • Cart and local inventory state are not synchronized between visitors or devices.
  • Clearing browser storage can reset demonstration inventory state.
  • CDN-hosted styling, icons, and fonts need internet access.

Possible future work includes accessibility and device-size testing, replacing CDN dependencies with local packages for offline demonstrations, improving product filtering and keyboard navigation, and adding a secure backend only if real orders or shared inventory are intentionally required.
