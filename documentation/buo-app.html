Buo — Strength Training & Fitness Progress App

A local-first Python/Kivy fitness application for strength logs, workout planning, recovery check-ins, reminders, personal records, analytics, exports, and optional Gemini-assisted guidance.

Download Buo Desktop Source ↧Back to Case StudyView Source README

1. Project overview

Buo is a local-first fitness and strength-training application. It is designed to help an individual record workouts, organize training, review recovery, keep personal notes, and monitor progress in one desktop application.

The portfolio package is focused on the Windows desktop presentation build. It contains the Python/Kivy source, a local SQLite data layer, Windows setup and launch scripts, the app icon, project notes, and an example configuration. It is source code, not a prebuilt Windows installer or Android APK.

2. Goals and core capabilities

Strength tracking

Record exercises, sets, repetitions, load, and effort fields such as RIR where available.

Workout planning

Organize training plans, workout-maker flows, and workout/rest timers.

Recovery and notes

Record recovery/wellness check-ins, reminders, and private journal notes.

Progress review

Review personal records and analytics; export selected data and make local backups.

AI-assisted guidance

Optionally use Gemini online when private configuration and internet access are available.

Offline fallback

Retain local coach behavior when online AI cannot be reached.

These capabilities are represented in the supplied source. Individual screens, calculations, and storage flows still require structured acceptance testing.

3. Application architecture

The Windows entry point is main.py, which imports main() from buo.app. The application module launches BuoApp from buo.legacy_ui.

main.py
  └── buo.app.main()
        └── BuoApp().run()
              └── buo.legacy_ui.BuoApp
                    ├── Kivy user interface
                    ├── SQLite data layer (DB)
                    ├── platform service helpers
                    └── optional Gemini request logic
  • buo/config.py defines project, asset, database, cloud-config, and local-sync paths.
  • buo/legacy_ui.py contains the main application class, screen-building logic, data access layer, and app interactions in this source snapshot.
  • buo/platform_services.py contains notification and Android-related helper functions.
  • service/background_tracker.py contains service-side tracker code; the current app-side launcher is not wired to run it.
  • requirements-desktop.txt pins the desktop Python dependencies.

4. Local data and SQLite

Buo uses SQLite for local application data. The database path is defined by DB_PATH in buo/config.py and resolves to buo.db in the project directory.

The local database is intended for personal information such as profile details, training logs, wellness/recovery records, reminders, journal entries, and settings. Treat it as private user data. The public source package intentionally excludes a real database. A database is created or initialized by the application when it starts.

Privacy: back up the database before replacing source files or testing migrations. Never commit buo.db, fitness exports, private journals, or personal backup bundles to a public repository.

5. Online Gemini AI and offline fallback

The Fitness AI Coach can call the Gemini REST API when a valid private API key, model identifier, and internet connection are available. The implementation reads private settings from cloud_config.json; the public repository contains an example configuration template only.

  • The API key is sent through the x-goog-api-key request header rather than embedded in the request URL.
  • Selected temporary network and service failures receive short retry attempts.
  • When an online request fails, the app can return to its offline coach behavior and expose a failure reason.
  • A configured key alone does not prove the service is available. HTTP 503, network failures, invalid model identifiers, and quota/rate-limit responses can still prevent a remote answer.
The owner demonstrated a successful Gemini HTTP 200 response in the Windows desktop app. This confirms at least one online request succeeded in the owner's environment; it does not prove every AI smart tool, prompt, model, or network condition has been tested.

6. Windows installation and launch

Requirements

  • Windows 10 or Windows 11, 64-bit.
  • Python 3.13 or 3.12, 64-bit.
  • Internet access for the initial dependency installation.

Setup

  1. Download and extract the Buo desktop source package.
  2. Open the extracted Buo project folder.
  3. Double-click setup_buo_windows.bat.
  4. Wait for virtual-environment and dependency installation to finish.
  5. Double-click run_buo_windows.bat.

The pinned desktop dependencies are:

kivy[base]==2.3.2
plyer==2.1.0
requests==2.32.3

Manual launch

Open PowerShell in the Buo project folder:

py -3.13 -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
python -m pip install -r requirements-desktop.txt
python main.py

If Python 3.13 is not installed but Python 3.12 is available, use py -3.12 when creating the environment. Keep the working directory at the project root because the app uses relative paths.

7. Optional private configuration

cloud_config.example.json is a placeholder. To enable Gemini locally, create a private cloud_config.json in the project root and enter the required Gemini API key and model identifier. Do not commit the real configuration file. Firebase/cloud-sync settings are optional and are not required for local SQLite use.

9. Known limitations

  • GPS route capture handlers and route/GPX helper functions are placeholders; the current helper functions return empty values.
  • BuoApp.start_background_tracking() returns False; the app-side Android background tracking service is not launched by this source snapshot.
  • start_background_tracking_service() and stop_background_tracking_service() in platform_services.py return False.
  • Android step-counter support is platform-specific and requires testing on a physical Android device.
  • Android notification and background-service behavior is not established by the Windows desktop build.
  • No Android APK or AAB is included in this desktop handoff.
  • Optional Gemini and Firebase features depend on private configuration and external service availability.
  • Plyer notifications may behave differently or be unavailable on Windows.
Do not describe GPS route tracking, GPX export, Android background continuity, or a tested Android release as complete based on this source snapshot.

10. Privacy, security, and future improvements

Buo may handle personal workout history, fitness measurements, recovery records, and private journal notes. Treat these as sensitive personal information.

Never publish buo.db, personal exports, private journals, local sync folders, cloud_config.json, real Gemini/Firebase credentials, or Android signing keys. Revoke and replace any API key that was previously exposed; removing it from a later commit does not invalidate an exposed credential.

Future improvements include completing Android packaging and permissions, implementing route/GPX features end to end, adding structured acceptance tests, improving data deletion/export controls, and adding privacy disclosures before wider distribution. If online AI is distributed to multiple users, use an appropriately authenticated server-side service rather than embedding a reusable API key in a client app.
