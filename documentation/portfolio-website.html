BSIT Professional Portfolio Website

This document explains the portfolio website as a complete system: its purpose, pages, content sections, front-end architecture, data files, project resources, maintenance workflow, deployment, and known limitations. It documents the portfolio platform itself, not just an individual project displayed inside it.

1. System overview

The BSIT Professional Portfolio is a browser-based website designed to present the portfolio owner's professional profile, technical skills, project work, evidence, problem-solving examples, cybersecurity awareness, responsible AI use, employability preparation, and career goals in one organized location.

The published edition is a static website intended for GitHub Pages. It uses client-side HTML, CSS, and JavaScript and reads portfolio content from a generated JavaScript data file. PHP, MySQL, or a server-side application are not required to display the portfolio.

Primary purpose

Present skills and project evidence in a structured professional portfolio.

Intended audience

Recruiters, employers, instructors, evaluators, collaborators, and visitors reviewing the owner's work.

Hosting model

Static files published from the repository through GitHub Pages.

Core data model

Portfolio content is maintained in JSON and generated into a JavaScript file for browser use.

2. Objectives and scope

Objectives

  • Present the portfolio owner's profile and professional direction.
  • Organize technical skills with supporting examples and evidence.
  • Show three project case studies and distinguish demos, source packages, reports, and limitations.
  • Record troubleshooting, cybersecurity, and responsible AI-use learning.
  • Support interview preparation, career planning, resume access, and project-defense rehearsal.
  • Provide a maintainable website that can be updated and published using Git and GitHub Pages.

Included

Public portfolio presentation, client-side navigation and theme selection, rendering of structured content, links to static evidence, individual project case-study pages, project documentation pages, a content-update guide, and a project-defense presentation view.

Not included in this static edition

Server-side user accounts, a private administrator dashboard, a shared database, server-stored contact messages, visitor file uploads, or backend transaction processing.

6. Architecture and data flow

data/portfolio.json is the editable source of structured portfolio content. The builder script reads that JSON and generates assets/js/default-data.js, which assigns the content to window.defaultPortfolio. The homepage and project pages load this generated data file and use JavaScript to render the relevant content.

data/portfolio.json
        │
        ▼
python tools/build_portfolio_data.py
        │
        ▼
assets/js/default-data.js
        │
        ├── index.html + assets/js/app.js
        ├── project.html (?id=0, ?id=1, or ?id=2)
        └── defense.html

HTML + CSS + JavaScript + static assets
        │
        ▼
GitHub repository → GitHub Pages static hosting
  1. The browser requests a static HTML page.
  2. The page loads the required stylesheets, JavaScript, data file, and assets.
  3. The scripts read window.defaultPortfolio.
  4. The homepage rendering functions populate the profile, skills, project cards, evidence, and other sections.
  5. project.html reads the id query parameter to select a project record.
  6. The theme script applies the visitor's selected color theme.

8. Update and preview workflow

  1. Open the local repository folder in VS Code.
  2. Edit data/portfolio.json. Keep valid JSON syntax and preserve required commas and quotation marks.
  3. From the repository root, run the build script:
python tools/build_portfolio_data.py

The script rewrites assets/js/default-data.js. Do not hand-edit the generated file because the next build will overwrite it.

Preview locally

python -m http.server 8000

Open http://localhost:8000. Stop the server with Ctrl + C in the terminal.

Publish

  1. Review changed files in GitHub Desktop.
  2. Commit the changes to the correct branch.
  3. Click Push origin.
  4. Confirm that GitHub Pages deployment succeeds, then test the live website.

See the content update guide for the shorter maintenance procedure.

9. Theme, local storage, and visitor interactions

  • Theme preference: light/dark appearance is handled in the browser. The selected theme is stored in that visitor's localStorage; it does not change the theme for other visitors.
  • Mobile navigation: the homepage includes a menu toggle for narrower screens.
  • Expandable content: project cards and troubleshooting cases use expandable sections.
  • Project defense: previous/next controls and keyboard left/right arrows move between steps. The browser print feature can print or save the view as PDF.
  • Checklist: in the updated build, checklist progress is stored locally in the visitor's browser. It is not a shared submission tracker and is not synchronized between devices.
  • Contact: email and social buttons open an external app or website. They do not submit messages to a portfolio server.

10. Hosting and deployment

The site is designed for GitHub Pages. The repository's configured publishing root must contain index.html and all referenced assets. The current setup uses the main branch and repository root.

  1. Commit the website files to GitHub.
  2. Open repository Settings → Pages.
  3. Choose the configured branch and folder for deployment.
  4. Save and confirm the Pages deployment succeeds.
  5. Open the published URL and test the homepage, project pages, documentation, resume, and evidence links.
GitHub Pages serves static files. It does not execute PHP or provide the portfolio with a MySQL database. Separate projects may require their own hosting or local runtime.

11. Security and privacy

  • Assume files committed to a public repository can be viewed and downloaded.
  • Never commit API keys, passwords, private tokens, personal IDs, private databases, confidential workplace records, or other information that should not be public.
  • Review resume and contact details before publication.
  • Keep credentials for separate projects outside the public portfolio repository.
  • Browser storage is local to one browser profile. Clearing site data can remove saved theme preference and checklist progress.
  • Check external links and downloadable files before publishing.

12. Limitations and future improvements

Current limitations

  • No server-side login, database, admin content manager, stored contact form, or server upload manager.
  • Content publication requires repository edits and a Git push.
  • Theme preference and checklist progress are browser-local, not shared across visitors.
  • Some styling resources are loaded from a public CDN and require an internet connection.
  • GitHub Pages does not run the separate Kivy desktop app or Streamlit analysis project.

Recommended future work

  • Test layouts and interactive controls in desktop and mobile browsers.
  • Check all project, documentation, resume, report, and workbook links.
  • Improve keyboard and screen-reader testing for navigation and expandable elements.
  • Consider hosting external CSS resources locally if offline presentation is required.
  • Use a secure backend only if shared accounts, stored messages, uploads, or centralized management become real requirements.

13. Verification checklist

Test the deployed version after the latest commit:

  • Homepage loads without missing styles, scripts, or images.
  • Main navigation and mobile menu work.
  • Light and dark themes remain readable.
  • Profile, skills, and project content are current.
  • All three project case-study pages open with the correct IDs.
  • Museum demo, TechZone files, and Buo source links resolve.
  • Project documentation pages are reachable from the website.
  • Resume and contact links are correct and safe to publish.
  • Defense Mode navigation and print view work.
  • Mobile layout is readable at common phone widths.

A source-code review alone does not prove that every live link or device layout works. Verify the published version in a browser.
